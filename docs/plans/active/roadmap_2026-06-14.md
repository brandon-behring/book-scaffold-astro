# Roadmap — `book-scaffold-astro`

**Original date:** 2026-06-14 · **Refreshed:** 2026-07-13 · **Original baseline:** v4.24.0 · **Published baseline:** v4.26.3 · **Status:** active

This is the post-reconciliation refresh tracked by #185. It preserves the
original roadmap's consumer-signal and design-before-code reasoning, while
absorbing the tracker work filed through #212, the v4.26 release repair, and
the active v4.27 stabilization batch.

Status terms in this document are deliberate:

- **Shipped** means the change is on `main`, tagged, and published in both
  lock-step npm packages.
- **In flight** means the contract is selected and implementation exists or is
  under review, but it is not part of a published v4.27 artifact yet.
- **Next** means active, evidenced backlog without a committed release.
- **Parked / on signal** means intentionally unscheduled until its recorded
  trigger fires; it is not forgotten work.

## v5.x gate — coherent scope

### Direction retained: corpus as monorepo (#80)

The independent-consumer trigger fired: `guides-ai-engineering` joined the
DLAI study-notes pilot as a second single-app, multi-guide consumer. The chosen
direction remains **one app, one build, multiple namespaced books**. It
graduates the way both consumers already operate instead of asking them to
federate independent deployments.

The cost model from the original roadmap still matters:

- Route injection is centralized in `ROUTE_REGISTRY`; adding book-aware route
  patterns is not principally a dispatcher rewrite.
- Profile schemas are selected independently; this is not principally a Zod
  union rewrite.
- The expensive surface is book-scoping the build products and validation:
  labels/counters, exercises, tips, references, route parameters, links,
  readiness counts, and search/navigation across a shared corpus.
- Federation remains an unfired, separate need. It would require a corpus-wide
  search index, landing/selector behavior, and deployment/base-prefix rules that
  neither signaling consumer requested.

The v4.26 book-aware navigation release is a no-regret slice of #80, not proof
that #80 is complete. A decision-complete scope document must precede v5 code
and settle:

1. the corpus/book manifest and profile-composition model;
2. route identities and `getStaticPaths` parameters for corpus landing,
   per-book chapter indexes, chapters, and apparatus routes;
3. book-scoped output keys and diagnostics for every build/validate command;
4. Pagefind indexing, result URLs, and navigation at both book and corpus level;
5. single-book compatibility and migration from recipe 21's `generateId`
   workaround; and
6. how #147, #158, and #190 compose with the corpus contract without being
   falsely treated as already implemented by it.

### Two deliberate v5 removals

| Issue | v4.27 compatibility bridge | v5 contract |
|---|---|---|
| #211 | `deploy` remains typed but is deprecated; an explicit unsupported top-level value warns. | Remove it from book/style types, built-in styles, docs, and tests, with a migration note. Deployment continues to be selected by real scaffold/deploy configuration rather than an inert promise. |
| #212 | Missing preset still falls back to `minimal` with one deprecation warning; explicit config/env/`.env` values are validated. | Require an explicit valid preset and fail with an actionable diagnostic when none resolves. |

These removals belong in the same v5 migration story as #80, but they do not
expand #80's implementation. #210 remains explicitly outside the multibook
scope.

## Sequencing guardrails

1. Finish and publish v4.27 stabilization before opening an invasive v5
   implementation branch.
2. Keep v4 changes additive or compatibility-preserving; use deprecation to
   make the two v5 breaks predictable.
3. Prioritize demonstrated consumer failure and shared duplication over small
   speculative features. Effort is a planning input, not the ordering rule.
4. Keep stable demo plumbing separate from volatile domain APIs.
5. Do not invent VersionSelector or Anki data contracts without a deployment or
   import workflow able to validate them.
6. Require a decision-complete #80 scope document and migration plan before v5
   route/tooling implementation.
